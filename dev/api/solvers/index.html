Solver reference

ProximalSolvers — Module
ProximalSolvers

Solvers for minimize f(x) + g(x), built on the functions and proximal operators of ProximalBase: ProximalGradientDescent, AccProxGradDescent, ActiveAccProxGradDescent and ADMMSolver for a proximable g, and coordinate descent (CDSolver, ProxNewton) for a separable one, all called through solve!. Before its first release the package was called ProximalOPT.

source
ProximalSolvers.solve! — Function
solve!(x, f, g, method::ProximalSolver, options = ProximalOptions())

Minimize f(x) + g(x) starting from x, and overwrite x with the solution.

For ProximalGradientDescent and AccProxGradDescent, f is a smooth function of ProximalBase (issmooth(f)) and g a proximable one (isproximable(g)), and x is an array of any shape that they accept, such as the p × k coefficient matrix of a LeastSquaresLoss with k responses and a NuclearNorm penalty; the result is an OptimizationResults. There x may also be a SparseIterate, or for the group lasso GroupNormL2 an AtomIterate that shares the groups of g (AtomIterate(x, g.groups)): the iterates keep its type, zeros are dropped after each step, and products by the iterates touch only their stored entries or active groups. For ActiveAccProxGradDescent, x is a vector, a SparseIterate or an AtomIterate, and the result is an ActiveSetResults. For ADMMSolver, both f and g are proximable and the result is an ADMMResults. For CDSolver and ProxNewton, see their documentation.

Example

using ProximalBase, ProximalSolvers
A, b = [2. 0.; 0. 1.], [-1., -1.]
x = zeros(2)
res = solve!(x, QuadraticFunction(A, b), NormL1(0.1), AccProxGradDescent())
source
solve!(x, f, g, method::CDSolver)

Minimize f(x) + g(x) by coordinate descent, starting from x, a SparseIterate, a SymmetricSparseIterate, or an AtomIterate with the groups of a group penalty g; x is overwritten with the solution. A dense vector x is converted to a SparseIterate (an AtomIterate for a GroupNormL2) and overwritten with the solution. Returns a CDResults. See CDSolver.

source
solve!(x, f, g, method::CDSolver; continuation, continuation_tol, screening)

With continuation = n > 0, x is set to zero and f + g is minimized along n penalty levels spaced geometrically from lambda_max down to the level of g, then at g itself, each warm started from the previous solution. The levels before g only give warm starts, so they are solved to the looser tolerance continuation_tol (√tol for the tolerance tol of method, by default), and only g to tol; continuation_tol = method.tol solves every level to tol. With screening, each level is screened with the strong rule (see solve_path); the default screens except on a SymmetricSparseIterate, whose coordinate steps update the gradient everywhere, so that the optimality checks of screening cost more passes than they save. When the level of g is zero or at least lambda_max, f + g is minimized from zero directly, and so it is for a penalty without a level (ZeroFunction, IndBox, …), which has no path.

ProximalSolvers.ProximalOptions — Type
ProximalOptions(; kwargs...)

Options for solve!. The solver stops at the first of: a convergence test passes, maxiter iterations, time_limit seconds, a limit on the number of calls, the objective increases (unless allow_f_increases), or callback returns true.

Keywords

  • maxiter = 200: maximum number of iterations.
  • ftol = 1e-6: stop when |F(x) - F(x')| / (|F(x)| + ftol) < ftol, where F = f + g and x' is the previous iterate.
  • xtol = 1e-8: stop when ‖x - x'‖ < xtol * max(‖x‖, 1).
  • gradtol = 1e-5: stop when the relative or normalized optimality residual of Goldstein, Studer and Baraniuk (FASTA) is below gradtol. Not used by ADMMSolver, which has its own tolerances.
  • allow_f_increases = false: keep iterating when the objective increases.
  • store_trace = false: record an OptimizationState per iteration in the results.
  • show_trace = false: print the progress every printEvery iterations.
  • extended_trace = false: also store the iterate and gradient in each state.
  • printEvery = 1: how often to print, store and call callback.
  • callback = nothing: a function called every printEvery iterations with the trace (if store_trace) or the current state; return true to stop.
  • time_limit = Inf: maximum run time in seconds.
  • f_calls_limit = 0, grad_calls_limit = 0, prox_calls_limit = 0: stop once f, the gradient of f, or proximal operators (prox!) have been evaluated this many times; 0 means no limit. The counts are checked after each iteration, which always finishes, so a count can exceed its limit by the evaluations of one iteration. ADMMSolver uses only prox_calls_limit.

The solvers work in the element type of the starting point, Float32 as well as Float64. Tolerances below its precision, such as ftol = 1e-8 in Float32 (eps(Float32) ≈ 1.2e-7), cannot be met: the solver then stops when rounding makes the objective increase, with converged false.

Proximal gradient solvers

ProximalSolvers.ProximalGradientDescent — Type
ProximalGradientDescent(; ls = LineSearches.BackTracking())

Proximal gradient descent (Parikh and Boyd, Proximal Algorithms, §4.2): x ← prox_{g/L}(x - ∇f(x) / L), with the step size 1/L chosen by the backtracking line search ls of TFOCS. Use with solve!.

source
ProximalSolvers.AccProxGradDescent — Type
AccProxGradDescent(; β = 0.5, α = 0.9)

Accelerated proximal gradient descent (Parikh and Boyd, Proximal Algorithms, §4.3). Each iteration extrapolates y = x + k/(k+3) (x - x') and takes a proximal gradient step from y; the step size 1/L is found by backtracking, shrinking it by the factor β ∈ (0, 1). Before each iteration L is multiplied by α ∈ (0, 1], so that the step grows again where the curvature is smaller, as in TFOCS; α = 1 keeps L from decreasing. On the lasso of the benchmark, α = 0.9 takes 1.2 to 6.5 times less time than α = 1.

The momentum restarts whenever the objective would increase (O'Donoghue and Candès, Adaptive restart for accelerated gradient schemes, 2015), so the objective is nonincreasing. Use with solve!.

source
ProximalSolvers.ActiveAccProxGradDescent — Type
ActiveAccProxGradDescent(; β = 0.5, α = 0.9, max_add = 100, growth = 2, max_outer = 1000)

Active-set accelerated proximal gradient descent, for f(x) + g(x) with a sparse minimizer, such as the lasso or the group lasso. The active set is the set of stored entries of a SparseIterate, or the set of active groups of an AtomIterate, whose coordinates are groups. Each outer iteration

  1. removes the coordinates that are zero from the active set (dropzeros!);
  2. computes the full gradient ∇f(x) and finds the coordinates outside the active set that violate the optimality conditions, kkt_violation > 0;
  3. stops if there are none and x minimizes f + g over the active set, that is, the last inner solve converged (or x = 0); an inner solve stopped by maxiter is thus repeated. It also stops after a converged inner solve that changed no entry of x: the next one would repeat it. This happens within rounding of the smallest penalty with a zero solution, where the check flags a coordinate that the proximal step leaves at zero;
  4. adds the violators to the active set (activate!), the largest violations first, until they hold max(max_add, (growth - 1) s) entries, where s is the number of entries left in the active set by step 1, and with them the violators whose violation equals the last one;
  5. minimizes f + g over the active set with AccProxGradDescent(; β, α), warm-started from the current values.

The limit in step 4 keeps the active set from filling up with the many coordinates that violate the optimality conditions at a poor starting point, such as zero for a small penalty: at each outer iteration the active set grows by a factor of at most growth over the nonzero entries of x, or by max_add entries if that is more. So it reaches a large support in a few outer iterations, but stays close to the support. growth = 1 adds max_add entries at a time, and max_add = typemax(Int) removes the limit.

Step 5 runs on restrict(f, S) and restrict(g, S) from ProximalBase, a problem in the active entries S only; step 2 is the only one that involves all coordinates. f and g need restrict, g needs kkt_violation, and f needs value_and_gradient! at the iterate: in ProximalBase these are, among others, QuadraticFunction, SqrNormL2, LeastSquaresLoss and GLMLoss, with NormL1, GroupNormL2, ZeroFunction and the other separable penalties.

For the group lasso GroupNormL2, an AtomIterate that shares the groups of g, AtomIterate(x, g.groups), makes the groups the coordinates: a group joins and leaves the active set whole. A dense x takes this route when the groups of g cover all coordinates. With a SparseIterate, the coordinates of a group at zero share the violation of the group, so a group that violates the optimality conditions joins the active set whole too.

max_outer limits the number of outer iterations. The ProximalOptions apply to each inner solve. Use with solve!, which returns an ActiveSetResults.

source
ProximalSolvers.LineSearches.BackTracking — Type
BackTracking(; α = 0.9, β = 0.5, Lexact = Inf)

The backtracking line search of TFOCS (private/tfocs_backtrack.m). Each iteration starts from L ← α L, where 1/L is the step size, and while the local Lipschitz estimate L̂ of the step exceeds L it retries with L ← min(Lexact, max(L̂, L / β)). L̂ comes from function values until they are too close to compare in floating point, and from gradients after that. A trial point where f is not finite, such as a matrix off the positive definite cone for LogDetLoss, is never accepted: it gives no estimate, and the search retries with L ← L / β.

The object holds settings only and can be shared between solves; the bookkeeping lives in the solver state.

The ADMM solver

ProximalSolvers.ADMMSolver — Type
ADMMSolver(; ρ = 1.0, α = 1.0, abstol = 1e-6, reltol = 1e-4, adaptive = false,
             abstol_dual = abstol, norm = nothing)

The alternating direction method of multipliers for f(x) + g(x) when both f and g have easy proximal operators (Boyd et al., Distributed Optimization and Statistical Learning via the Alternating Direction Method of Multipliers, 2011). It splits x = z and iterates

x ← prox_{f/ρ}(z - u)
z ← prox_{g/ρ}(α x + (1 - α) z + u)
u ← u + α x + (1 - α) z_previous - z

ρ > 0 is the augmented Lagrangian parameter and α ∈ (0, 2) the over-relaxation (α = 1 is plain ADMM; 1.5 to 1.8 usually converges faster). It stops when the primal residual ‖x - z‖ is below √n abstol + reltol ⋅ max(‖x‖, ‖z‖) and the dual residual ρ‖z - z_previous‖ below `√n abstol_dual

  • reltol ⋅ ρ‖u‖(§3.3 of the paper). Withadaptive,ρ` balances the two

residuals (§3.4.1): it doubles when the primal residual, relative to its tolerance, is more than ten times the dual one, halves in the opposite case, and stays fixed after 50 changes, which keeps the convergence guarantee of a fixed ρ.

norm is the norm in which the residuals and ‖x‖, ‖z‖ and ‖u‖ are measured, a function of an array; nothing is the Euclidean norm. A stacked array of K blocks, for example, can be measured by the sum of the norms of its slices, x -> sum(k -> LinearAlgebra.norm(view(x, :, :, k)), axes(x, 3)). If norm also has a method norm(x, y) for the norm of x - y, the residuals are measured with it, without forming the differences.

Of the ProximalOptions, only maxiter, time_limit, prox_calls_limit, show_trace and printEvery are used. Use with solve!; to warm start from a previous result res, pass its scaled dual variable and final penalty parameter: solve!(x, f, g, ADMMSolver(; ρ = res.ρ), options; u = res.u).

Coordinate descent solvers

ProximalSolvers.CDSolver — Type
CDSolver(; maxpasses = 100_000, tol = 1e-7, order = :random, relative = true, anderson = 0,
           momentum = nothing, rng = Random.default_rng())

Coordinate descent for f(x) + g(x), where g is separable (isseparable(g): NormL1, ElasticNet, MCP, SCAD, IndBox, …) or a group penalty such as GroupNormL2 on an AtomIterate with its groups, and f is a loss whose structure solve! recognizes: LeastSquaresLoss, a least-squares GLMLoss, QuadraticFunction, KronQuadratic, or one of these scaled, as in (1/n) * LeastSquaresLoss(y, X).

Each pass visits the coordinates once, in random order (order = :random, drawn from rng) or in the order 1, 2, … (order = :cyclic). The first pass visits all coordinates. After a full pass that changes some coordinate by more than tol, passes over the active ones (the stored entries of the iterate) follow until one changes none by more than tol, and then another full pass. The method stops after a full pass in which no coordinate changes by more than tol, or after maxpasses passes. With relative, the change of coordinate k is measured as |Δxₖ| √aₖ, where aₖ is the curvature of f along the coordinate, and compared with tol times a scale of the data, so that the tolerance does not depend on the units of the data (for least squares, ‖X[:, k]‖ √s and ‖y‖ √s for f = s ‖y - Xβ‖² / 2).

With anderson = K > 0 and order = :cyclic, the passes over an unchanged active set are accelerated by Anderson extrapolation (Bertrand and Massias, Anderson acceleration of coordinate descent, AISTATS 2021): every K + 1 such passes, the iterates on the active set are extrapolated, and the extrapolated point is kept if it decreases f + g. On the lasso designs of the benchmark, CDSolver(; order = :cyclic, anderson = 5) takes 1.6 to 2.6 times less time than cyclic order alone at 0.02 λmax. A random order changes the map of a pass from one pass to the next, which the extrapolation needs to repeat, so anderson is ignored with it, as on an AtomIterate. Strongly correlated columns still favor a random order.

With momentum, each pass over the active set starts from the extrapolated point xₖ + βₖ (xₖ - xₖ₋₁), with Nesterov's βₖ = (k - 1) / (k + 2), as in CoordinateDescent.jl 0.6. The momentum restarts after a full pass, when the active set shrinks, and when the step of a pass points against it (O'Donoghue and Candès, Adaptive restart for accelerated gradient schemes, 2015). Full passes are never extrapolated, so the method stops on a plain full pass. The cache of a built-in model moves with the point, at the cost of a few vector operations per pass; a model of another loss is initialized at the extrapolated point. By default (momentum = nothing) it is used with the random order on a SparseIterate for LeastSquaresLoss, GLMLoss, SqrtLeastSquaresLoss, QuadraticFunction and SqrtQuadraticFunction, and not otherwise. momentum = true asks for it with any model on a SparseIterate or a SymmetricSparseIterate, such as KronQuadratic; momentum = false turns it off. With the cyclic order it can stall far from the minimizer, so order = :cyclic refuses momentum = true.

The random order is drawn from rng, by default the task-local generator of Random.default_rng(), which draws exactly as the global generator does, so that Random.seed! makes a run reproducible. A generator of its own, such as Xoshiro(1), makes the passes reproducible without reseeding the global one, and separate generators give parallel solves independent streams. The solver keeps a reference to rng, so solves with the same solver advance the same generator; don't share one generator between tasks.

ProximalSolvers.ProxNewton — Type
ProxNewton(; inner = CDSolver(; tol = 1e-8), maxiter = 100, tol = 1e-8, β = 0.5)

Proximal Newton for f(x) + g(x), f a GLMLoss (or a scaled one) and g a separable penalty, as glmnet fits generalized linear models: each step minimizes the quadratic model of f at x, a weighted least-squares loss with the weights wᵢℓ''(ηᵢ) and the working responses ηᵢ - ℓ'(ηᵢ)/ℓ''(ηᵢ), plus g, by coordinate descent (inner) warm started from x, and then backtracks along the step on f + g, shrinking it by β, until the objective decreases. It stops when the objective changes by less than tol relative to its value, or after maxiter steps. Use with solve! on a SparseIterate; returns CDResults, whose passes sum the inner passes.

f may also be the model of a GLMLoss built with cdmodel(f, x; intercept = true), which fits an unpenalized intercept β₀ as well, as the intercept of the weighted least-squares model of each step: η = Xβ + β₀ + o. The model keeps β₀ (read it with intercept(m, x)) and starts the next solve from it. solve_path takes ProxNewton too.

Result types

ProximalSolvers.OptimizationResults — Type
OptimizationResults

Returned by solve! for ProximalGradientDescent and AccProxGradDescent. Its fields include minimizer, minimum (f + g at the minimizer), iterations, the flags x_converged, f_converged, grad_converged, f_increased and iteration_converged (the iteration limit was reached), the final residuals x_residual, f_residual and g_residual with their tolerances, the trace, backtrack_steps, the number of trial steps checked by the backtracking line search over all iterations (accepted steps included), and the number of evaluations: f_calls of f (by value or value_and_gradient!), grad_calls of its gradient and prox_calls of the proximal operator of g. call_limit_reached is true when the solver stopped at one of the limits in ProximalOptions. The minimizer is the x passed to solve!: an Array, a SparseIterate or an AtomIterate.

source
ProximalSolvers.ActiveSetResults — Type
ActiveSetResults

Returned by solve! with an ActiveAccProxGradDescent: minimizer (the x passed to solve!), minimum (f + g at the minimizer), outer_iterations, inner_iterations (summed over the inner solves), converged (no coordinate outside the active set violates the optimality conditions, and the last inner solve converged), inner_converged (every inner solve converged), max_violation (the largest kkt_violation outside the active set at the minimizer, -Inf if there is no such coordinate) and active_set_size (the number of entries in the active set, those of its groups for an AtomIterate).

source
ProximalSolvers.ADMMResults — Type
ADMMResults

Returned by solve! with an ADMMSolver: minimizer, minimum (f + g at the minimizer), iterations, converged, the final primal and dual residuals r_norm, s_norm with their tolerances eps_pri, eps_dual, the scaled dual variable u and the final penalty parameter ρ (for a warm start), and the number of evaluations: f_calls of the value of f (for the trace and minimum), grad_calls (always 0) and prox_calls of the proximal operators of f and g. call_limit_reached is true when the solver stopped at prox_calls_limit (see ProximalOptions).

source
ProximalSolvers.CDResults — Type
CDResults

Returned by solve! for a CDSolver: the minimizer (the iterate passed in), the minimum f + g at it, the number of passes, whether the stopping rule was met (converged), the largest scaled change of a coordinate in the last pass (maxchange) and the tolerance it was compared with, and kkt_checks, the number of times the optimality conditions of the coordinates left out by screening were checked.

source
ProximalSolvers.OptimizationState — Type
OptimizationState{T<:ProximalSolver}

One iteration of a trace: iteration, the objective fg_x = f(x) + g(x), the relative change dxx = ‖x - x'‖ / ‖x‖, the inverse step size L, and a metadata dictionary that holds the iterate and gradient when extended_trace = true.

source
ProximalSolvers.OptimizationTrace — Type
OptimizationTrace{T}

A Vector{OptimizationState{T}}, stored in the results when store_trace = true (see ProximalOptions).
